This file analyses the reference design, compares it against Mori,
and decides what Mori adopts, defers, or rejects. It is **not** a
re-implementation plan. The implementation plan lives in
[`docs/memory-architecture.md`](../memory-architecture.md) and
[`docs/roadmap.md`](../roadmap.md).

## Reference architecture

```
                    ┌───────────────────────────┐
                    │   Memory Orchestrator     │
                    │   (Root ADK agent)        │
                    └──────────────┬────────────┘
                                   │ routes
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
      ┌───────────────┐   ┌────────────────┐   ┌────────────────┐
      │ IngestAgent   │   │ ConsolidateAgent│   │ QueryAgent     │
      │ multimodal    │   │ 30-min default  │   │ natural-language│
      │ extract       │   │ insight/merge   │   │ answers + cites │
      └──────┬────────┘   └────────┬────────┘   └────────┬───────┘
             │ writes               │ writes              │ reads
             ▼                      ▼                     ▼
      ┌─────────────────────────────────────────────────────────┐
      │  SQLite (memory.db)                                     │
      │  - memories(id, source, raw_text, summary, entities,    │
      │             topics, importance, connections,            │
      │             consolidated, created_at)                   │
      │  - consolidations(source_ids, summary, insight, …)      │
      │  - processed_files(filename, hash, …)                   │
      └─────────────────────────────────────────────────────────┘

        Inbox folder (./inbox/) ── watched ──► IngestAgent
        HTTP POST /ingest        ── direct ──► IngestAgent
        Dashboard upload         ── direct ──► IngestAgent
        HTTP GET  /query?q=…     ── direct ──► QueryAgent
        HTTP POST /consolidate    ── manual ──► ConsolidateAgent
```

### Roles

- **Memory Orchestrator (Root Agent)** — ADK root that routes each
  inbound message to one of three specialist agents. Owns the
  request lifecycle but holds no memory of its own.
- **IngestAgent** — runs Gemini's multimodal extraction on every new
  artifact. Emits `{summary, entities, topics, importance}` per item
  and inserts a row into `memories`. Stores the original text /
  multimodal hash for provenance.
- **ConsolidateAgent** — fires on a default 30-minute timer (or
  manually via `POST /consolidate`). Reads unconsolidated rows from
  `memories`, asks the LLM to (a) find cross-cutting connections,
  (b) generate higher-level insights, (c) compress related rows. The
  output lands in `consolidations`; the source rows are flipped to
  `consolidated = 1` so they're not double-processed.
- **QueryAgent** — answers natural-language questions by reading the
  full set of memories + consolidation insights and synthesising a
  citation-bearing reply. There is no embedding index — every query
  reads the whole table.

### Storage

| Table | Purpose | Notes |
| ----- | ------- | ----- |
| `memories` | One row per ingested artifact. | Carries `raw_text` by default (no automatic redaction). |
| `consolidations` | One row per consolidation pass. | `source_ids` is a JSON array; `insight` is LLM-generated copy. |
| `processed_files` | File-watcher dedupe state. | Filename + content hash. |

### Ingestion

- **File watcher** (`./inbox/`) — auto-pulls 27 file types within
  5–10 seconds of drop. Includes images, audio, video, PDFs.
- **HTTP API** (`POST /ingest`) — accepts inline text + a `source`
  tag.
- **Dashboard upload** — Streamlit UI that wraps the HTTP API.

Every inbound artifact is processed by the LLM immediately; no
review-before-apply step. Importance score is generated by the LLM
itself.

### Consolidation

- Runs on a configurable timer (`--consolidate-every 30`).
- Reads up to ~10 unconsolidated rows per pass.
- Asks the LLM to identify connections, generate an insight string,
  and mark the source rows as consolidated.
- Manual trigger via `POST /consolidate`.

### Query

- `GET /query?q=...` reads **all** memories + recent consolidations
  and asks the LLM to synthesise an answer with `[Memory N]`
  citations. No vector retrieval. No top-K filter.

### Claimed benefits

- No vector database / embedding pipeline → smaller ops surface.
- Continuous consolidation produces insights that vector RAG misses
  ("static retrieval vs. dynamic memory").
- Cheap + fast with Flash-Lite as the consolidation runner.

## Comparison: Reference vs. Mori

| Concern | Reference (Always-On Memory Agent) | Mori |
| ------- | ---------------------------------- | ---- |
| **Trigger to capture** | Drop file in inbox or POST text. Auto-ingested by LLM within ~10 s. | Explicit paste / desktop inbox load. Always goes through Import Review. |
| **Review-before-apply** | None. LLM writes to `memories` immediately. | Mandatory. Import Review is a non-bypassable gate. |
| **Capture surfaces** | Filesystem watcher (any file), HTTP API, dashboard upload. Multimodal. | AI Transcript, Connector JSONL (paste or `~/.mori/connectors/`), Git Diff, Manual Note, URL — all user-initiated. Text only today. |
| **Identity / dedupe** | File hash in `processed_files`; otherwise the LLM is the dedupe layer. | `connectorEventId` (`<connectorId>::<session>::<id>`) + identity overlay. Pure code, no LLM. |
| **Evidence / provenance** | One free-form `source` string per row. | Typed `SourceRef` with kind, trust level, redaction status, raw-data retention policy, captured-at, connector privacy boundary. |
| **Consolidation** | Scheduled LLM pass every 30 min by default. | None scheduled. Quick Pass runs on demand (per session) and writes `MoriAnalysisResult` + a `StoredSessionMemoryBody`. Project Memory aggregates these across sessions, also on demand. |
| **Query** | LLM reads the whole DB + insights and answers. | Project Memory view-model + Resume Prompt builder produce a copy-pasteable continuation prompt. No in-app natural-language query. |
| **Long-term store** | SQLite (`memory.db`). | Browser localStorage + desktop SQLite + `.mori v0` export. Schema-versioned. |
| **Multimodal** | Yes (text, image, audio, video, PDF). | No. Text-only events today. |
| **LLM dependency** | Required for ingest, consolidate, and query. Hard dep on Gemini. | Optional. Quick Pass has a deterministic fallback. Resume Prompt is pure local derivation, no LLM call. |
| **Privacy posture** | No documented privacy boundary. `raw_text` retained by default. No mention of secrets, redaction, or consent. | Privacy is a first-class concern. `rawDataPolicy`, `redactionStatus`, secret-pattern detection, no cloud sync, no background watching, no external account access. |
| **Failure modes documented** | None. | Each layer carries warnings (`metadataOnly`, `failed`, `partialLoad`, `import-summaries-unavailable`, etc.) and the UI surfaces them. |
| **Operational shape** | Long-running daemon (`python agent.py`). | Browser SPA + optional Tauri desktop shell. No daemon. |
| **Cost model** | LLM cost per ingest + every 30 min indefinitely. | Zero per-minute cost. LLM only spent on explicit Quick Pass. |

## What Mori should adopt

These ideas translate well to Mori's local-first, evidence-first model.

1. **Three-role mental model** — Ingest / Consolidate / Query is a
   useful naming convention. Mori already has all three; documenting
   them with these names makes the architecture easier to reason
   about. The naming lands in
   [`docs/memory-architecture.md`](../memory-architecture.md).
2. **Explicit `consolidated` flag on stored memories** — useful
   pattern. When Mori grows a user-triggered "consolidate Project
   Memory" pass (Phase 2 on the roadmap), `StoredSessionMemoryBody`
   should carry a `consolidatedAt` marker so re-runs skip stable
   memories.
3. **Citations in synthesised output** — Mori already attributes rows
   to sessions in the Resume Prompt (`sessionId` / `sessionTitle`).
   A future natural-language query layer should preserve that
   discipline.
4. **Separation between raw memory rows and synthesised insight
   rows** — the reference's `consolidations` table is a different
   shape from `memories`. Mori's analogue is the split between
   `StoredSessionImport.events` (raw) and `MoriAnalysisResult`
   (synthesised). The split is already correct; documenting it
   explicitly closes a comprehension gap.
5. **Manual consolidation endpoint** — `POST /consolidate` is a useful
   pattern for the user-triggered consolidation milestone. Mori would
   expose this as a UI button, not an HTTP endpoint.
6. **One simple storage layer** — SQLite without vectors / embeddings
   is honestly enough for the personal-scale workload. Mori already
   chose this direction; the reference validates it.

## What Mori should explicitly reject for now

These are non-goals — see [`docs/roadmap.md`](../roadmap.md) and the
per-milestone briefs that excluded them.

1. **Always-on background ingestion**. Mori's product premise is
   work-session reconstruction with **explicit evidence**. Watching
   filesystems for any-file-any-type drop dilutes the trust model and
   violates the user-consent posture.
2. **LLM-as-dedupe**. Connector dedupe runs on stable identities, not
   on summarisation similarity. Letting an LLM decide whether two
   events are "the same" introduces hallucinated merges and
   non-deterministic state.
3. **Skipping a review gate**. Every Mori import passes through
   Import Review. The reference design has none. We won't remove
   Import Review even when Phase 2 ships a consolidation pass — the
   user reviews consolidation proposals too.
4. **Storing `raw_text` by default with no retention policy**. Mori
   already has `rawDataPolicy` per connector event. The reference's
   "store everything" default is incompatible with the user-trust
   contract Mori advertises.
5. **Cloud / Vertex AI dependency**. Mori runs against Ollama / a
   local Codex-style provider / an optional OpenAI-compatible
   endpoint that the user supplies. No vendor lock-in.
6. **Multimodal ingestion**. Out of scope for the personal work-memory
   product today. Text + structured connector events is enough.

## What Mori should defer (research / Phase 2+)

Defer means "consider for a later milestone, after the explicit-
import loop is stable".

1. **User-triggered consolidation pass over Project Memory.** Today
   `buildProjectMemoryViewModel` derives memory live from the active
   + saved sessions. A "consolidate" action could:
   - merge near-duplicate decisions across sessions,
   - promote recurring issues to a project-level entity,
   - mark stale memories, surface conflicts, and request user review
     before applying.
   This is Phase 2 in the roadmap.
2. **Local query layer.** Currently the only query surface is the
   Resume Prompt builder. A small local query helper that answers
   "what did we decide about X?" with citations into Mori sessions
   is plausible — but it should obey the same redaction / privacy
   policy as Resume Prompt, never expose raw connector text by
   default, and never reach an external endpoint.
3. **Optional opt-in inbox watcher.** A user-installed daemon (or a
   Tauri-side watcher) could auto-load the existing connector inbox
   directory (`~/.mori/connectors/`) into a "Pending review" tray.
   The new files would still go through Import Review before reaching
   Project Memory. Phase 3 on the roadmap.
4. **Memory promotion / demotion lifecycle.** The reference's
   binary `consolidated` flag is fine for prototypes. Mori's analogue
   should track a richer state: `proposed → reviewed → promoted →
   stale → retired`, with user confirmation required between
   `proposed` and `promoted`.
5. **Per-project memory partitioning.** Today Project Memory derives
   from sessions filtered by the active project. Multi-project
   browsing across the Memory page is plausible later.

## Risks the reference exhibits, and how Mori avoids them

| Risk | Reference exposure | Mori mitigation |
| ---- | ------------------ | --------------- |
| Privacy creep | No retention policy, raw text stored, watcher on by default. | Explicit `rawDataPolicy`, redaction helpers, no watcher, no auto-ingest. |
| Always-on capture | Daemon + filesystem watcher by default. | No daemon. Explicit user action per import. |
| Hallucinated consolidation | LLM merges memories every 30 min; no user review. | No consolidation pass yet. When one ships, it runs on demand and is reviewed before applying. |
| Source drift | One free-form `source` string. | Typed `SourceRef` + connector identity + import summary. |
| Duplicate / contradictory memories | LLM is the only dedupe layer. | Connector identity-based dedupe runs in pure code. |
| Unclear user consent | No surface explains what the LLM did. | Data-basis badge + warnings strip + load-status indicators per session. |
| Cloud dependency | Hard Gemini dependency. | Optional local LLM; everything except LLM is deterministic local code. |

## Mori interpretation table

If you read the reference vocabulary, here's where the equivalent
lives in Mori today.

| Reference concept | Mori equivalent | File / surface |
| ----------------- | --------------- | -------------- |
| Memory Orchestrator (root agent) | `sessionStore` + `MemoryView` orchestration | [`src/app/sessionStore.ts`](../../src/app/sessionStore.ts), [`src/features/memory/MemoryView.tsx`](../../src/features/memory/MemoryView.tsx) |
| IngestAgent | Connector / AI-transcript / Git-diff / Manual-note import path | [`src/lib/connectors/`](../../src/lib/connectors/), [`src/features/import/`](../../src/features/import/) |
| Review gate (none in reference) | Import Review | [`src/features/review-import/ImportReviewView.tsx`](../../src/features/review-import/ImportReviewView.tsx) |
| Per-row evidence/provenance (one-string `source`) | `SourceRef` with trust + retention + redaction + connector identity | [`src/domain/types.ts`](../../src/domain/types.ts), [`src/lib/sources/`](../../src/lib/sources/) |
| ConsolidateAgent | Quick Pass (per session) + Project Memory aggregation (cross session) | [`src/lib/analysis/`](../../src/lib/analysis/), [`src/lib/project-memory/`](../../src/lib/project-memory/) |
| Memory store | localStorage + SQLite + `.mori v0` | [`src/lib/storage/`](../../src/lib/storage/), [`src/lib/sqlite/`](../../src/lib/sqlite/), [`src/lib/mori-package/`](../../src/lib/mori-package/) |
| QueryAgent (`/query?q=…`) | Resume Prompt builder | [`src/lib/project-memory/projectMemoryResumePrompt.ts`](../../src/lib/project-memory/projectMemoryResumePrompt.ts) |
| Citations in answer | `sessionId` + `sessionTitle` attribution on every aggregated row | [`src/lib/project-memory/crossSessionAggregation.ts`](../../src/lib/project-memory/crossSessionAggregation.ts) |
| Inbox folder | `~/.mori/connectors/` inbox (still user-initiated load) | [`src-tauri/src/connectors/inbox.rs`](../../src-tauri/src/connectors/inbox.rs), [`docs/imports.md`](../imports.md) |

The shapes line up but **the contracts differ**: every Mori layer
adds an explicit user-consent step or a typed evidence boundary
where the reference relies on LLM-on-by-default behaviour.
